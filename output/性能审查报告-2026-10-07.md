# 心灵信箱 · 首屏性能审查报告（2026-10-07）

> 审查范围：miniprogram 全部 12 页、app.js 启动链路、services 数据层、13 个云函数。  
> 结论先行：**首屏渲染架构本身已经做得很到位**（骨架屏、服务端聚合、setData 投影、多级缓存、信封预取、批量埋点等），本次发现的优化空间集中在三处——**主包体积、云函数冷启动、素材格式**。

---

## 一、按影响程度排序的问题清单

### P0-1｜主包体积 1.8MB，信封素材占近 1MB，逼近 2MB 主包上限

- **位置**：`miniprogram/assets/theme/`（16 套主题 × 大图 + 缩略图，实测 898KB）；`assets/qrcode.jpg` 44KB；`assets/mailbox.png` 48KB。全包 1.8MB，代码约 0.8MB。
- **原因**：所有主题的 `envelope.jpg`（52–60KB/张）都打进主包，而小程序主包需在**首次启动与版本更新后**完整下载并注入。1.8MB 已达主包上限的 90%，再上新主题素材就会编译失败，且每次发版用户都要重新下载接近 2MB 的包。
- **方案（二选一，可叠加）**：
  - **方案 A（推荐，根治）**：大图下沉云存储。16 张 `envelope.jpg` 上传云存储 → 后台 theme 集合 `assets.envelope` 改为 `cloud://` fileID → 包内只留 `envelope-thumb.jpg`（约 180KB），大图从包里删掉。代码侧零改动：详情页两级 src（`envSrc` 首帧小图 + `envFull` 预取大图）、`prefetchEnv`、`envFade` 云图淡入这套机制天然支持 `cloud://`（admin 后台编辑抽屉本来就允许填 fileID）。注意 `themes.js` 本地回落配置同步改为 fileID；离线极端情况大图缺失时回落 thumb，已有兜底链（`envelopeThumb || envelope`）不会白屏。
  - **方案 B（低成本，止血）**：全部大图用 mozjpeg/squoosh 按 q72–75 重压（890×616 → 约 35–40KB/张），素材 898KB → 约 600KB，零代码改动。
- **预期提升**：方案 A 主包 1.8MB → 约 0.95MB，首次启动下载体积 **-47%**；弱网（2Mbps）下载约 7s → 3.8s，4G 约 1.4s → 0.8s；并为后续新主题腾出约 1MB 空间。方案 B 素材约 -33%。

### P0-2｜首页 onShow 每次无条件全量刷新，重复调用 today 云函数

- **位置**：`miniprogram/pages/home/home.js` `onShow → loadMailbox()`。
- **原因**：每次从详情/写信返回、Tab 切回，都会重新 `Promise.all(today.mailbox + getThemes + getMembership)`。其中 `today.mailbox` 每次必发——短时间内信件数据几乎不会变化，这是典型的高频重复请求；云函数按次计费且冷启动场景下用户要白等 1–2s。
- **方案**：给 `loadMailbox` 加一个轻量时间闸（如 30s 内已拉过且没有 `letter_just_arrived` 标记时跳过重拉，只重算本地能算的倾角/今日来信）。寄出回传、下拉等显式动作绕过闸门强制刷新。
- **预期提升**：today 云函数调用量下降约 40–60%（视使用习惯）；热路径返回信匣从「等一次云函数往返」变成零等待；冷启动场景下二次进入省 0.3–1.5s。

### P1-3｜themes 与 papers 拆成两次云函数调用

- **位置**：`miniprogram/services/theme.js` `getThemes()` / `getPapers()`；`cloudfunctions/theme`（list / papers 两个 action）。
- **原因**：详情页 `loadLetter` 的 `Promise.all` 里 `getThemes + getPapers` 各打一次 `theme` 云函数（1h 缓存过期后必发两枪）。两者同源（同一集合族、同一容器），没有理由拆两次往返。
- **方案**：theme 云函数新增 `all` action 一次返回 `{themes, papers}`（papers 现含 member_items 聚合，可同次并发完成）；`theme_cache` / `papers_cache` 合并为一份缓存、同一 TTL；保留旧 action 兼容已发版客户端。
- **预期提升**：详情/写信第二步每次进页省一次云函数调用（热调用约 100–200ms，冷启动场景可达秒级）；云函数调用次数相应下降。

### P1-4｜today.mailbox 云函数内部：封禁检查串行 + 信件查询无字段投影

- **位置**：`cloudfunctions/today/index.js` 第 31 行 `await isBanned()`，第 38–43 行 letters 查询。
- **原因**：① `isBanned`（一次 users 查询）先 await 完才开始查草稿数与信件，串行多一次 DB 往返；② letters 查询把 `answer`（单封最长 2000 字）、`replies`、`opens` 整文档拉进函数内存，随后只投影出 5 个字段——100 封信匣时白拉白序列化约 200KB。
- **方案**：`isBanned` 并入 `Promise.all`（封禁是运营管控非安全边界，函数内注释已明确此口径，迟到几毫秒返回 banned 无碍）；letters 查询加 `.field({ name:1, theme_id:1, pinned:1, created_at:1, today_letter_of:1 })`（`_id` 默认返回；孤儿认领与 today_letter_of 写回只依赖这些字段，已核对可行）。
- **预期提升**：函数执行时间 -10~50ms（信件越多越明显）；DB 出网流量约 -90%；属稳定性优化，量大时防劣化。

### P1-5｜app.js 启动链路：建档 → 预热串行，多一次云函数往返

- **位置**：`miniprogram/app.js` 第 19–25 行：`ensure` 完成后 `then(() => userService.prefetch())`。
- **原因**：`ensure`（user 容器冷启动 + 建档写入）完成后才发出 `getProfile` 与 `stats.get`，预热被推迟了一个完整云函数往返（冷启动约 0.6–1.5s）。而 `getProfile` 对无建档用户本就回落默认值，服务端口径安全。
- **方案**：`ensure` 与 `prefetch()` 并行发出（prefetch 内部的 getProfile 顺带兜底建档语义即可）。若要更彻底：把 ensure 的建档并入 `getProfile` 的 upsert，启动期 user 云函数只调一次。
- **预期提升**：「我的」页预热提前约 0.5–1.5s 到位（冷启动场景），切 Tab 首屏命中率显著提高；启动期少一个串行等待。

### P2-6｜素材格式：12 张 baseline JPEG + 48KB PNG + 44KB 二维码

- **位置**：`assets/theme/` 下 cuican/daoying/gonglu/luori/shanye/tiantan 六套的大图与缩略图共 12 张为 baseline（非渐进式）；`assets/mailbox.png` 48KB（首页空态/悬浮信箱）；`assets/qrcode.jpg` 44KB（仅分享图用）。
- **原因**：素材规格要求渐进式 JPEG，六套旧主题未达标；mailbox.png 是照片类内容却存成了无损 PNG。
- **方案**：旧六套重新导出为渐进式并顺手按 P0-1 方案 B 压缩；mailbox.png 转 jpg/webp（预计 48KB → 15KB 内）；qrcode.jpg 重压（二维码对比度高，q80 无损观感）。
- **预期提升**：素材总体再省约 60–80KB；渐进式保证弱网下图片由糊到清渐进呈现，不出现半截灰块。

## 二、已达标、不建议再动的部分（避免无效优化）

- **首页冷启动骨架**：`home.json` 的 `initialRenderingCache: static` + 骨架色块，数据 onShow 拉取（onLoad 不重复拉）。
- **setData 投影**：信匣列表只带渲染字段，question/answer 全文不进渲染层，序列化体积与信件数解耦。
- **服务端聚合**：today 一次返回信匣 + 草稿数 + 今日来信，草稿计数与列表已并发查询。
- **详情单轮往返**：拆信记录并入 `letter.get`（record 参数），渲染路径只有一轮云函数。
- **多级缓存**：theme/papers 1h storage 缓存、member 30s 内存缓存、profile/stats 内存缓存 + 启动预热、epoch 防串号。
- **信封首帧链路**：handoff 同步交接 + 两级 src + 入口页 `prefetchEnv` + 云图淡入，已是同类需求的完整方案。
- **埋点**：5 条/15s 批量上报，失败静默重试，不占主流程。
